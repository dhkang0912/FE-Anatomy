# 브라우저 렌더링 과정
## (1) 개요
- 웹 성능의 주요한 문제
  1. 지연 시간
  2. 브라우저가 대부분 싱글 스레드로 동작한다는 점
    - 메인 스레드가 요청된 모든 작업을 수행하면서도 유저와의 상호작용에 반응할 수 있도록 보장하기 위해서는 `렌더링 시간`이 가장 중요
    - 메인 스레드의 책임을 줄여주는 방식으로 웹 성능 향상을 이룰 수 있음


## (2) 탐색 (Navigation)
- 웹 페이지를 로딩하는 첫 단계
- 사용자가 주소창에 URL을 입력하거나 링크를 클릭하고 폼을 제출하는 등의 동작을 통해 요청을 보낼 때마다 발생
- `웹 최적화의 목표` 중 하나는 `탐색이 완료될 때까지 시간을 최소화`하는 것

### 1. DNS 조회 (DNS Lookup)
- 웹 페이지 탐색의 첫 단계로 해당 페이지의 자원이 어디에 위치하는 지 찾는 것
- url을 통해 HTML 페이지 IP 주소를 확인하고 한번도 방문한 적 없다면 DNS 조회를 함
  - ![alt text](<URL 구조.png>)

<br>

- DNS 조회 순서
1. 브라우저에 의한 DNS 조회 요청 
2. 이름 서버에 의해 처리 
3. IP 주소로 응답 
4. 최초 요청 후 IP는 일정 기간 동안 캐시 
5. 이름 서버에 다시 연락하는 대신 캐시를 통해 IP 주소 탐색하여 후속 요청 속도를 높임

<br>

- DNS 조회는 보통 호스트 이름 하나당 한번만 수행되지만 요청 페이지에서 참조하는 다른 호스트 이름에 대해서는 각각 수행해야함
  - 예 : 글꼴, 이미지, 스크립트, 광고 그리고 다른 자원들이 서로 다른 호스트 이름을 가지고 있다면 DNS 조회는 각각 진행됨
  - 모바일 네트워크 환경에서 성능 문제가 될 수 있음
    -  DNS 조회 > 휴대폰 > 셀타워 > DNS 서버로 전송되는 과정에서 지연시간이 발생할 수 있음

### 2. TCP 핸드셰이크 (TCP HandShake)
- 브라우저가 서버에 요청을 보내기 전에 신뢰할 수 있는 안전한 네트워크 연결 수립을 위해 TCP 핸드셰이크와 TLS 협상이 이뤄짐
- IP 주소를 알고난 후 브라우저 `서버`와 `TCP 3방향 핸드셰이크`를 통해 `연결`을 설정함
  - 데이터를 전송하기 전 `HTTPS`를 통해 통신하려는 브라우저와 웹 서버가 TCP 소켓 연결을 위한 `매개변수`를 주고 받을 수 있음
    - TCP 소켓 : 클라이언트(브라우저)와 서버가 데이터를 주고 받기 위해 설정하는 `네트워크 연결`
      - TCP 핸드셰이크를 통해 이 소켓이 연결됨

<br>

- TCP의 3방향 핸드셰이크 기술 (SYN-SYN-ACK) 
  - TCP 3방향 핸드셰이크 : 데이터 전송 전 클라이언트(브라우저)와 서버 간 연결을 설정하는 과정
    - 서버와 클라이언트가 데이터 전송 전에 서로를 확인하고 안정적인 연결을 보장하기 위해 필요하며 이 과정이 없으면 패킷이 손실되거나 순서가 뒤바뀔 위험이 있음
    - TCP : 인터넷에서 데이터를 신뢰성 있게 전송하는 프로토콜
  - TCP 3방향 핸드셰이크 과정 (SYN -> SYN-ACK -> ACK)
    - 두 컴퓨터 간 TCP 세션을 협상하고 시작하기 위해서 TCP가 3개의 메시지를 전달
    - 요청이 보내기 전 3개의 추가적인 메시지가 컴퓨터 사이에 주고 받아진다는 것을 의미함
    1. 클라이언트 -> 서버 : SYN (요청 보내기)
       - 클라이언트가 서버에 연결을 시작하고 싶다는 신호인 SYN 패킷을 보냄
    2. 서버 -> 클라이언트 : SYN-ACK (수락 및 응답 보내기)
       - 서버가 요청을 받고 연결을 시작하겠다는 응답인 SYN-ACK 패킷을 보냄
    3. 클라이언트 -> 서버 : ACK (연결 확인하기)
       - 클라이언트가 서버의 응답을 확인한 후 데이터 전송을 시작한다는 ACK 패킷을 보냄
    - 위의 과정이 모두 완료되면 TCP 연결이 완료된 것이며 클라이언트와 서버가 데이터를 주고 받을 준비가 된 것

### 3. TLS 협상 (TLS Negotitation)
- TCP 연결이 설정되면 보안이 강화된 HTTPS 연결을 위해 TLS 핸드셰이크를 진행함
- TLS (Transport Layer Security) : 데이터를 암호화하여 안전한 통신을 보장하는 프로토콜
  - HTTPS에서 사용되며 데이터가 해킹당하지 않도록 보호함
  - TLS 협상을 통해 암호화된 보안 연결을 설정
  - TLS 핸드셰이크는 모든 데이터를 암호화하여 보호하며 데이터 전송 중 해킹되거나 변조될 가능성을 방지해줌
- TLS 협상을 위한 핸드셰이크 (HTTPS 연결 설정)
  - HTTP를 이용한 보안성 있는 연결을 위해 필요
  - 통신 암호화에 쓰일 암호를 결정하고 서버를 확인하고 실제 데이터 전송 전에 안전한 연결이 이루어지도록 함
  - 자원에 대한 실제 요청 전 클라이언트 서버로 3번 더 왕복하게 됨 (TLS 1.3 기준)
  1. Client Hello (클라이언트 -> 서버) : TLS 연결 시작 요청 및 키 교환
     - 브라우저가 서버에게 TLS 연결을 사용하고 싶다는 요청을 보냄
     - 지원 가능한 암호화 목록과 키 교환 정보 등 아래와 같은 여러 정보를 포함하여 함께 보냄
       - 지원 가능한 암호화 목록인 사이퍼 스위트 (Cipher Suite)
       - 키 교환(ECDHE, Ephemeral Diffie-Hellman) 정보
       - 랜덤 데이터(Client Random)
       - TLS 1.3을 사용할 것이라는 점
  2. ServerHello + Certificate + Finished (서버 → 클라이언트) : TLS 연결 수락 및 인증서 전송
     - 서버가 클라이언트의 요청을 받고 응답을 보냄
     - 보낼 내용
       - 선택한 암호화 알고리즘(Cipher Suite)
       - 키 교환(ECDHE) 정보
       - 서버 인증서(Server Certificate, HTTPS 인증서)
       - 핸드셰이크가 완료되었음을 알리는 Finished 메시지
  3. Finished (클라이언트 → 서버)
     - 클라이언트가 서버의 응답을 확인한 후 Finished 메시지를 보냄
  - 위 과정이 완료되면 TLS 보안 연결이 확립되고 HTTPS를 통해 암호화된 데이터를 주고 받을 수 있음

<br>

- TLS 협상 핸드셰이크의 경우 연결에 보안성을 더한 것이라 페이지 로딩을 더디게 하지만 제 3자가 전송되는 데이터를 해독할 수 없게 하기 때문에 지연시간을 감내할 가치가 있음

## (3) 응답 (Response)
- 웹 서버로 한번 연결이 성립되고 나면 브라우저는 유저 대신에 초기 `HTTP GET request`를 보냄
  - HTML 파일을 요청함
  - 서버가 요청을 받으면 관련 응답 헤더와 함께 HTML 내용을 응답하게 됨

<br>

- TTFB (Time to First Byte) : 사용자가 요청을 보내고 HTML의 첫 패킷을 받는데 걸린 시간
  - 첫번째 컨텐츠 청크는 일반적으로 `14kb` 크기의 데이터

### 3-1. 혼잡 제어(Congestion control) / TCP 슬로우 스타트 (TCP Slow Start)
- `서버와 클라이언트가 데이터를 전송`할 때 한번에 전송되지 않고 작은 단위 (TCP 세그먼트)로 `분할되어 전송`됨
  => TCP 패킷은 전송 중에 세그먼트로 분할됨
- TCP는 `패킷의 순서를 보장`하기 때문에 서버는 일정 개수의 세그먼트를 전송한 후 `클라이언트`로부터 `ACK 패킷(Acknowledgment Packet) 형태로 승인`을 받아야 함
  - ACK 패킷 : 신뢰성 보장을 위해 `확인 응답`을 보내는 것으로 `ACK 번호 (정상적으로 받은 마지막 데이터의 다음 순서 번호)`와 `현재 수용 가능한 윈도우 크기`를 같이 보냄

<br>

- 서버가 모든 세그먼트를 각각 ACK를 기다리면 클라이언트로부터 빈번히 ACK를 발생하고 저부하 네트워크 상황이라도 전송 시간을 증가시킬 수 있음  
  => 여러 세그먼트에 대해 한 번의 ACK로 응답, 누적 ACK를 사용
- 한번에 너무 많은 세그먼트를 보내면 클라리언트에 보내면 클라이언트가 받을 수 있는 데이터 양인 윈도우 크기가 초과됨  
  -> 세그먼트를 받을 수 없어 계속 ACK(윈도우 크기 = 0)만 응답하게 되고 서버는 세그먼트를 계속 재전송해야하는 문제가 발생할 수 있음

<br>

- TCP 슬로우 스타트 알고리즘 : 전송되는 세그먼트 수의 균형을 맞추기 위해 사용됨
  - 최대 네트워크 대역폭이 결정될 때까지 전송되는 데이터 양을 점차적으로 늘리고 네트워크 부하가 높은 경우 전송되는 데이터 양을 줄임  
    => 즉, 초기에 너무 많은 데이터를 보내 네트워크를 과부하시키지 않게 점진적으로 전송 속도를 증가시키며 `최적의 전송 속도`를 찾는 알고리즘

<br>

- TCP 슬로우 스타트 동작 과정
  1. 초기 전송량 설정 (혼잡 윈도우 CWND = 1MSS)
     - 서버는 처음 작은 양의 데이터(보통 1MSS 크기)만 보냄 
       - MSS : Maximum Segment Size, 보통 1460 바이트, 한번에 보낼 수 있는 최대 크기의 세그먼트
     - 클라이언트가 데이터를 정상적으로 받으면 ACK를 보냄
  2. ACK를 받을 때마다 전송량을 두 배로 증가 (지수적 증가)
     - 서버는 ACK를 받으면 혼잡 윈도우(CWND)의 크기를 두 배로 증가
       - 예 : 1 MSS -> 2 MSS -> 4 MSS -> 8 MSS...
       - 정상적으로 전달되면 (네트워크가 계속 안정적이라면) 계속 두배씩 증가하는 방식
  3. 네트워크 혼잡 발생 시 속도 감소 (CWND 절반으로 줄임)
     - 네트워크가 혼잡해서 패킷이 손실되면 (ACK가 안 오면) TCP 전송량을 줄임
     - 혼잡이 감지되면 CWND 값을 절반으로 감소 
       - 예 : 16 MSS -> 8 MSS 
     - 이후 다시 슬로우 스타트 또는 혼잡 회피 단계로 전환됨
  4. 슬로우 스타트 또는 혼잡 회피 단계로 전환
     - 1) 혼잡이 발생하지 않은 경우 => 혼잡 회피 단계로 전환됨
        - 슬로우 스타트가 끝나면 CWND (혼잡 윈도우 크기)가 너무 빠르게 증가하는 것을 방지하기 위해 속도를 천천히 증가시키는 단계로 이동함
          - 최대 전송 속도를 유지하면서도 네트워크 상태를 고려해 속도를 점진적으로 늘림
        - 혼잡 회피에서 CWND 증가 속도를 선형적으로 완화하여 네트워크 안정성을 유지 (매번 1 MSS씩 증가)
          - 네트워크가 허용할 수 있는 최대 속도를 유지하면서 천천히 조절하는 과정
        - 슬로우 스타트에서 CWND가 특정 임계값(임계 혼잡 윈도우, ssthresh)을 넘어서면 슬로우 스타트가 끝나고 혼잡 회피 모드로 전환
     - 2) 혼잡이 발생한 경우 => 다시 슬로우 스타트로 돌아감
       - 네트워크가 혼잡해져 패킷 손실이 발생하면 TCP는 다시 속도를 낮추고 슬로우 스타트로 돌아감
       - 네트워크가 안정적인지 다시 확인하고, 속도를 재조정할 수 있음
  
<br>

- 브라우저가 로딩되는 과정 동안 네트워크 상태는 계속 변화하기 때문에 지속적으로 슬로우 스타트와 혼잡 회피를 반복하며 네트워크 상태를 모니터링하고 최적의 속도를 찾아가게 됨

## (4) 구문 분석 (Parsing)
- 브라우저가 첫번째 데이터의 청크를 받으면 수신된 정보를 구문 분석함
  - 구문 분석
    - HTML, CSS, Javascript의 구조를 해석하여 브라우저가 이해할 수 있는 데이터로 변환하는 과정
    - 브라우저가 네트워크를 통해 받은 데이터를 DOM이나 CSSOM으로 바꾸는 단계 => 렌더러가 화면에 페이지를 그리는데 사용
- 브라우저는 마크업을 내부적으로 DOM으로 표현
  - DOM은 공개되며 Javascript의 다양한 API를 통해 조작됨
- 브라우저는 HTML 파일을 한번에 다 받지 않아도 먼저 받은 초기 패킷인 14kb로 바로 분석 (파싱)하고 렌더링을 시도함
  - 그래서 웹 성능 최적화를 위해 첫 14kb 안에 핵심 HTML 구조와 CSS (첫 화면을 그리는데 필요한 내용)을 포함하는 것이 중요함

<br>

- 브라우저의 점진적 렌더링 과정
  - 데이터가 모두 도착해야 렌더링하는 게 아니라 `도착한만큼 렌더링`함
  - 패킷이 도착하면 받은 만큼 파싱을 시작함
    - HTML, CSS, Javascript를 구문 분석하고 DOM을 먼저 구성하고 렌더링을 시도함
  - 다음 패킷이 도착하면 브라우저는 해당 패킷의 데이터를 구문 분석하고 그 결과를 기존 DOM에 추가하면서 렌더링을 업데이트함
  - 위 과정을 페이지의 모든 HTML이 완성될 때까지 반복

<br>

- 화면에 렌더링하기 전 HTML, CSS, Javascript를 구문 분석해야함

### 1. DOM 트리 구축 (Building the DOM tree, 중요한 렌더링 1 단계) 
- HTML을 처리하기 위해 DOM (Document of Model) 트리를 만듦
- HTML 구문 분석 과정
  1. 토큰화 (Tokenization)
     - HTML 문서를 작은 단위(토큰)로 분해하는 과정
     - HTML 코드를 문자 단위로 읽고 이를 토큰이라는 작은 단위로 변환
     - 토큰은 HTML의 요소, 속성, 텍스트 등을 의미함
     - 이 과정에서 각 태그, 속성, 값이 각각 개별적인 토큰으로 처리됨
  2. 트리 생성 (Tree Construction)
     - 토큰화된 데이터를 조합하여 DOM 트리를 생성하는 과정
     - HTML 토큰을 분석하여 부모-자식 관계를 가진 트리 구조 (DOM Tree)를 만듦
     - 트리를 브라우저가 화면을 렌더링하는데 사용함
- 구문 분석기
  - HTML 코드를 해석하여 토큰화하고 이를 조합하여 DOM 트리를 생성하는 프로그램
  - 브라우저의 HTML Parser가 이 역할을 수행
  - HTML 문서를 읽으면서 토큰화 -> 트리 생성을 반복하여 DOM을 구성
  - 이 과정에서 CSSOM, JavaScript 실행도 함께 이뤄짐

<br>

- DOM 트리는 문서의 내용을 설명함
  - 트리는 다른 태그 간의 관계와 계층을 반영
  - 다른 태그에 감싸져 있는 태그는 자식 노드
  - DOM 노드의 개수가 많아질수록 DOM 트리를 만드는데 시간이 오래 걸림
  - HTML 요소 : 시작하는 태그, DOM 트리의 루트 노드
  - ![alt text](<DOM Tree.png>)

<br>

- 구문 분석기가 이미지와 같은 논 블로킹 자원을 발견하면 브라우저는 해당 자원을 요청하고 분석을 계속함
  - 논 블로킹 자원 : 이미지, CSS 파일, 폰트, `async(비동기)`나 `defer(지연 실행)`가 있는 `<script>` 태그, 미디어 파일 등
- 기본적으로 `async`나 `defer` 같은 설정이 되지 않은 `<script>` 태그는 HTML 분석을 중지시키는 `블로킹 요소`로 HTML 분석을 멈추고 JavaScript 파일을 다운로드하고 실행하게 함 
  - 브라우저 프리로드 스캐너라는 기능을 사용해 HTML 파싱 도중 필요한 리소스를 미리 요청할 수 있도록 가속화할 수 있지만 과도한 스크립트는 여전히 주요한 병목 구간이 될 수 있음

#### 1-1. 프리로드 스캐너 (Preload scanner)
- 메인 스레드 
  - DOM Tree 생성, CSSOM 생성, JavaScript 실행, 렌더링 등 브라우저의 주요 작업을 담당
  - HTML을 구문 분석하면서 DOM을 만듦
  - 브라우저가 DOM Tree를 만들 때 사용하는 프로세스는 메인 쓰레드를 활용함
- 네트워크 스레드
  - HTTP 요청 및 응답을 처리하는 역할
  - 프리로드 스캐너는 네트워크 스레드를 활용하여 백그라운드로 실행됨
    - 메인 쓰레드와 별도로 실행되며 외부 리소스(CSS, JavaScript, 웹 폰트 등)를 미리 요청함
      - 이후 브라우저의 네트워크 스케줄러에 따라 리소스의 우선순위를 결정하여 다운로드를 수행
    - 프리로드 스캐너를 통해 메인 쓰레드가 HTML을 다 읽고 리소스를 요청하기까지 기다리지 않도록 하여 속도를 향상시킴
    - 즉, 메인 스레드가 HTML 다 읽기 전 중요한 리소스를 미리 요청하여 속도를 향상함

### 2. CSSOM 구축 (Building the CSSOM, 중요한 렌더링 2 단계)
- CSSOM (CSS Object Model)
  - 브라우저가 CSS를 해석(파싱)하여 트리 구조로 만든 객체 모델
    - CSS 규칙을 해석하여 어떤 요소에 어떤 스타일을 적용할지 구조화한 모델
  - HTML의 DOM과 유사하지만 CSS 스타일 정보만 포함
  - 최종적으로 DOM과 결합하여 화면을 렌더링하는데 사용됨

<br>

- CSSOM 생성 과정
  1. CSS 다운로드
     - 브라우저가 HTML을 파싱하면서 `<link rel="stylesheet"> `태그를 만나면 CSS 파일을 다운로드함
  2. CSS 구문 분석 -> CSSOM 트리 생성
     - 브라우저는 CSS 코드를 읽고 트리 구조로 변환
     - CSS 선택자를 기반으로 부모-자식-형제 관계를 정의하여 트리 노드를 생성

<br>

- CSSOM이 스타일을 적용하는 과정
  - 사용자 에이전트 스타일 시트를 포함
    - 사용자 에이전트 스타일 시트 : 웹 브라우저가 가진 모든 웹 페이지에 기본적으로 적용되는 내장 CSS 스타일 시트
  - 가장 일반적인 규칙부터 적용하고 더 구체적인 규칙을 재귀적으로 수정   
    => 캐스케이드 (Cascade) : 스타일 우선순위를 결정하는 과정

<br>

- CSSOM 생성과정은 매우 빠르게 처리되어 성능에 미치는 영향이 적음
- 한번의 DNS 조회보다도 짧은 시간에 CSSOM이 생성되어 큰 성능 병목이 되지 않고 성능 최적화에 큰 영향을 미치지 않음

### 3. 다른 작업들 (Other Processes)
#### 3-1. JavaScript 컴파일 (JavaScript Compilation)
- 프리로드 스캐너를 통해 CSS가 분석되고 CSSOM이 생성되는 동안 JavaScript 파일 같은 다른 자원도 `다운로드`됨
  - `defer`, `async`가 붙지 않은 경우 
    - `다운로드된 이후 자바스크립트의 싱글스레드 특성 상 바로 실행됨`
    - 자바스크립트가 실행되면 DOM 트리 파싱은 중단됨
    - 자바스크립트 실행이 완료되면 DOM 트리 구축이 재개되고 이후 DOM과 CSSOM 파싱이 모두 완료되면 렌더 트리로 결합되어 화면에 렌더링함
  - `defer`, `async`가 붙은 경우
    - `defer`의 경우
      - HTML 파싱과 병렬로 자바스크립트 다운
      - 자바스크립트 실행은 `DOM 파싱이 끝난 후 실행됨`
      - HTML 문서가 완전히 파싱된 후, `defer`의 스크립트들이 순서대로 실행됨
    - `async`의 경우
      - HTML 파싱과 병렬로 자바스크립트 다운
      - 다운로드가 끝나는 즉시 실행되어 실행 순서가 보장되지 않고 `다운로드 속도에 따라` 자바스크립트가 먼저 `실행`될 수도 있음
      - 실행 순서에 따라 DOM 트리 파싱을 중단할 수도 있음
- JavaScript는 해석, 컴파일, 구문 분석 및 실행됨
  - 스크립트는 구문 분석기를 통해 `추상 구문 트리 (AST, Abstract Syntax Tree)`로 구문 분석됨
  - 일부 브라우저 엔진은 인터프리터를 통해 추상 구문 트리가 분석됨
  - 추상 구문 트리는 인터프리트 되어 직접 실행되거나 컴파일 되어 바이트 코드로 변환되어 실행됨

#### 3-2. 접근성 트리 구축 (Building the Accessibility Tree)
- 접근성 트리 (Accessibility Object Model)
  - AOM (접근성 트리) : 웹페이지의 의미(semantic meaning)를 포함하는 트리, DOM의 의미적 버전으로 화면에 표시되는 요소들이 의미적으로 어떻게 사용될지를 정의하는 구조
    - AOM은 보조 기술(예: 스크린 리더기)이 웹 콘텐츠를 이해할 수 있도록 제공하는 트리
    - 브라우저는 DOM을 생성한 후 추가적으로 접근성 트리를 생성하고 DOM이 업데이트될 때 접근성 트리도 함께 업데이트
      - 참고 : DOM - 웹페이지의 구조를 나타내는 트리

## (5) 렌더 (Render)
- 렌더링 과정 : 브라우저가 HTML, CSS, JavaScript를 처리하여 화면에 실제로 그리는 과정
  - 4가지 주요 단계 : 스타일 -> 레이아웃 -> 페인트 -> 합성
  - CSSOM과 DOM 트리는 구문 분석되는 과정에서 생성되고 `렌더 트리`로 합성됨
  - 렌더 트리는 보이는 요소의 레이아웃을 계산하고 요소가 화면에 페인트됨
  - 특정 경우에는 컨텐츠가 자신만의 레이어를 가지게 되고 나중에 합성됨
  - CPU와 함께 GPU를 화면 일부를 그리는데 사용하면 메인 쓰레드의 부담이 줄고 성능이 향상됨

### 1. 스타일 (Style, 중요한 렌더링 3 단계)
- 렌더 트리 (스타일 트리) 생성
  - `DOM과 CSSOM을 합쳐` 만들어지며 `화면에 표시될 요소`들만 포함하여 트리를 생성함
  - DOM 트리의 루트부터 시작하여 눈에 보이는 노드를 순회하며 만들어짐
  - 화면에 나타나지 않는 태그들은 렌더 트리에 포함되지 않지만 hidden 처럼 자리를 차지 하는 요소들은 렌더 트리에 포함됨
  - `<script> 태그`는 사용자 에이전트 스타일 시트 상 기본적으로 화면에 직접 표시 되지 않기 때문에 임의의 조작이 없다면 렌더 트리에 포함되지 않음

<br>

- 렌더 트리는 보이는 모든 노드의 내용과 계산된 스타일을 가지고 있음
  - DOM 트리에서 보이는 모든 노드에 관련된 스타일을 맞춰보고 CSS 캐스케이드 방식에 따라 각 노드의 계산된 스타일이 무엇일지 결정함

### 2. 레이아웃 (Layout, 중요한 렌더링 4 단계)
- 레이아웃 
  - 렌더 트리에 있는 모든 노드의 너비, 높이, 위치, 객체의 크기와 위치를 처음 결정하는 프로세스
  - 렌더 트리가 한번 만들어지면 레이아웃이 시작됨
    - 렌더 트리는 보이지 않더라도 계산된 스타일과 함께 어떤 노드가 화면에 표시될지 식별하지만 각 노드의 위치나 좌표를 알지 못함
    - 각 객체의 정확한 크기와 위치를 결정하기 위해서 브라우저는 렌더 트리의 루트부터 시작하여 순회
    - 레이아웃 단계에서 뷰포트와 본문과 모든 후손의 크기를 각 요소의 박스 모델 속성을 통해 계산
    - 단, 이미지와 같이 크기를 모르는 요소를 위해서 위치 표시 공간을 남겨둠
- 리플로우
  - 레이아웃 이후 노드의 크기와 위치를 다시 계산하는 것
  - 예 : 첫 레이아웃 완료 후 이미지가 온 경우 이미지 크기를 알게 된 후 리플로우가 발생

### 3. 페인트 (Paint, 중요한 렌더링 5 단계)
- 페인팅
  - 레이아웃 단계에서 계산된 각 박스를 실제 화면의 픽셀로 변환하고 텍스트, 색깔, 경계, 그림자 및 버튼이나 이미지 같은 대체 요소를 포함하여 모든 요소의 시각적인 부분을 화면에 그리는 작업
  - FMP (First Meaningful Paint) : 페인팅이 처음 일어나는 것, 이 이후 사용자는 웹 페이지를 유용하다고 느낄 수 있음

<br>

- 자연스러운 화면 전환 및 페인팅
  - 부드로운 스크롤이나 애니메이션을 위해서는 스타일 계산, 리플로우, 페인팅과 같이 메인 쓰레드를 점유하는 모든 작업이 브라우저의 16.67ms 미만 차지 해야함
  - 첫 페인팅보다 다시 페인팅하는 것이 더 빠르게 마무리 되기 위해서는 화면에 그리는 작업을 여러개의 레이어로 구분하게 되고 합성이 필요함

<br>

- 페인팅은 레이아웃 트리의 요소를 레이어로 분리할 수 있음
- CPU의 메인 쓰레드에서 페인팅하지 않고 GPU 레이어로 승격하면 GPU가 직접 페인트를 담당하여 성능이 향상됨
- 아래 특정 요소는 GPU에서 처리하도록 별도의 레이어를 생성할 수 있음
  - HTML 요소 : `<video>`, `<canvas>`
  - CSS 속성 : opacity, 3D transform, will-change
  - 단, 자손 노드가 별개로 자신만의 레이어를 필요하다면 불가능
- 레이어는 성능을 향상시키지만 메모리 관리 측면에서는 비용이 많이 드는 작업으로 웹 성능 최적화 전략으로 과도하게 사용하면 안됨

### 4. 합성 (Compositing)
- 합성 : 문서의 각 섹션이 다른 레이어에서 그려질 때 섹션을 겹치면서 올바른 순서로 화면에 그려지는 것과 정확한 렌더링을 보장하기 위해 사용됨

<br>

- 페이지가 계속 자원을 로드하면 요소들의 위치와 크기 계산을 다시 하며 리플로우가 발생하고 그로 인해 리페인트와 재합성을 일으킬 수도 있음

## (6) 상호작용 (Interactivity)
- 브라우저가 렌더링을 완료했어도 지연된 JavaScript 다운로드나 onload 이벤트에서 실행되는 코드가 있는 경우 `메인 쓰레드는 계속 작업을 수행해야돼서 여전히 바쁠 수 있음`
  - 지연된 JavaScript 다운로드 : async, defer, 동적으로 추가된 스크립트 등
  - onload 이벤트 : 페이지의 모든 리소스(이미지, CSS, JavaScript 등)가 로드된 후 실행되는 이벤트  
  => 이렇게 메인쓰레드가 여전히 실행되고 바쁘면 `스크롤링, 터치 등 다른 상호작용 불가능`

<br>

- TTI (Time to Interactive) : DNS 조회와 SSL 연결이 이루어지는 첫 요청부터 페이지가 상호작용할 준비가 될 때까지 걸리는 시간
  - FCP 이후 페이지가 사용자와 상호작용에 50ms 이내로 응답할 때 상호작용이 가능한 지점으로 봄
    - FCP (First Contentful Paint) : 페이지가 실제로 로드되고 있다는 첫 번째 피드백을 사용자에게 제공하는 경우, FCP 이후에 사용자는 웹 페이지가 로드되어 있다는 것을 느낄 수 있음
  - 메인 쓰레드 점유를 되도록 피해서 상호작용이 될 수 있도록 해야 사용자 만족도와 성능이 향상됨

<br>

## (7) 전체 순서 로드맵 
![alt text](<브라우저 렌더링 과정.png>)
1. 탐색
  - DNS 조회 : 첫 방문한 경우 URL 이름을 통해 IP 주소를 확인하고 캐시에 저장
  - TCP 핸드셰이크 : 브라우저가 서버에 요청을 보내기 전 신뢰할 수 있는 안전한 네트워크 연결 수립하기 위해 클라이언트와 서버 간 연결을 설정함
  - TLS 협상 : 보안이 강화된 HTTPS 연결을 위해 클라이언트와 서버가 암호화된 보안 연결 설정
2. 응답 : 웹 서버로처음 연결된 이후 HTML 파일 요청
  - 혼잡 제어 : 세그먼트 단위로 클라이언트와 연결 가능한 상태인지 ACK와 윈도우 크기를 응답 받으며 확인
  - TCP 슬로우 스타트 : 지속적으로 안정적인 네트워크 연결을 위해 점진적으로 전송되는 세그먼트 수를 늘렸다가 부하가 걸리면 줄임
3. 구문 분석
  - DOM 트리 구축 : 토큰화 -> 토큰 조합 후 구문분석기를 통해 <mark>DOM 트리 생성</mark> 
    - 프리로드 스캐너 : DOM Tree가 생성되는 도중에 메인 쓰레드가 아닌 네트워크 쓰레드를 통해 백그라운드로 CSS, JavaScript, 웹 폰트 등 자원을 다운로드 함
  - CSSOM 구축 : 토큰화 -> 토큰 조합 후 구문분석기를 통해 <mark>CSSOM 생성</mark>
    - DOM 트리와 병렬적으로 CSSOM 생성
  - JavaScript 컴파일 : 토큰화 -> 토근 조합 후 구문 분석리를 통해 <mark>추상 구문 트리 생성</mark>
    - `defer`, `async`와 함께 사용된 경우 지연 다운로드됨
    - 그렇지 않은 경우 프리로드 스캐너에 의해 다운로드된 이후 바로 실행되어 DOM Tree 생성 중단, JavaScript 실행 완료 후 DOM Tree 재생성
  - 접근성 트리 구축 : DOM Tree, CSSOM의 정보를 통해 의미적인 요소를 기반으로 생성됨
4. 렌더 : 브라우저가 HTML, CSS, JavaScript를 처리하여 화면에 실제로 그리는 과정
   - 스타일
     - 렌더 트리 생성 : DOM Tree와 CSSOM이 생성되면 둘이 합성되어 `렌더 트리`가 됨
   - 레이아웃 : 렌더 트리에 있는 모든 노드의 너비, 높이, 위치, 객체의 크기와 위치를 처음 결정하는 프로세스 
     - 리플로우 : 레이아웃 이후 노드의 크기와 위치를 다시 계산하는 것
   - 페인트 : 레이아웃 단계에서 계산된 각 박스를 실제 화면의 픽셀로 변환하고 텍스트, 색깔, 경계, 그림자 및 버튼이나 이미지 같은 대체 요소를 포함하여 시각적인 부분을 화면에 그리는 작업
     - 페인팅 시 레이아웃 트리의 요소를 레이어로 분리할 수 있음
   - 합성 : 레이아웃 트리의 요소를 레이어로 분리한 경우 문서의 각 섹션이 다른 레이어에서 그려질 때 섹션을 겹치면서 올바른 순서로 화면에 그려지는 것과 정확한 렌더링을 보장하기 위한 과정
5. 상호작용 : 렌더링 이후 사용자가 각 요소들과 상호작용할 수 있는 단계
   - TTI : DNS 조회와 SSL 연결이 이루어지는 첫 요청 (탐색, 응답 과정)부터 페이지가 상호작용할 준비가 될 때까지 걸리는 시간
   - FCP : 페이지가 실제로 로드되고 있다는 첫 번째 피드백을 사용자에게 제공하는 시기
   - 상호작용이 원활히 이뤄지기 위해서는 렌더링 이후 메인 쓰레드 점유를 되도록 피해야 함

## Q&A 
### Q1. url을 브라우저에 검색하거나 링크를 클릭하면 어떻게 해당 주소로 이동하는지 설명해주세요.
A1. 사용자가 URL을 입력하거나 링크를 클릭하면 첫 방문하는 경우 브라우저는 도메인을 찾기 위해 DNS 조회를 하고 IP 주소를 조회합니다. 이후 캐시에 IP를 저장하고 향후 동일한 웹사이트를 방문하는 경우 캐시 정보를 확인하여 빠르게 IP 주소를 가져옵니다.

IP 주소를 찾으면 TCP 핸드셰이크를 통해 서버와 신뢰할 수 있는 연결을 수립하고 HTTPS인 경우 TLS 협상을 통해 보안 연결을 합니다. 

이후 연결이 설정되면 브라우저는 서버에 HTTP GET 요청을 보내고 HTML, CSS, JavaScript 등의 파일을 응답한 후 브라우저 렌더링 과정이 진행됩니다.

### Q2. 브라우저 렌더링 과정에 대해 설명해주세요.
A2. 네트워크가 연결됐다면 메인 스레드를 통해 HTML이 파싱되어 DOM Tree를 생성합니다. 이 때 네트워크 스레드를 통해 백그라운드에서 프리로드 스캐너가 실행되어 CSS, JavaScript, 웹 폰트 등 여러 자원이 함께 다운됩니다. 이렇게 CSS 파일이 다운되면 CSSOM 트리를 병렬적으로 생성하고 JavaScript 파일이 다운되면 이를 실행하는 동안 DOM Tree는 중지됐다가 JavaScript가 실행이 완료되면 다시 생성합니다. 

DOM Tree와 CSSOM 트리가 모두 생성되면 접근성 트리인 AOM이 생성되고 스타일 단계로 진입해 렌더 트리로 결합되어 렌더링이 진행되게 됩니다. 

렌더 트리가 생성되면 노드의 크기와 위치, 배치를 결정하는 레이아웃 트리를 생성하게 되고 이후 페인트 단계에서 모든 노드들을 실제 픽셀 단위로 화면에 그리게 됩니다. 페인트 시 만약 레이아웃 트리를 레이어로 나눴다면 이후 합성을 통해 적절한 섹션에 배치할 수 있게 합성을 하게 됩니다.

위의 모든 과정이 끝나면 FCP 상태로 화면에 그려지게 되고 사용자는 브라우저와 상호작용할 수 있게 됩니다. 

### Q3. 리플로우와 리페인트에 대해 설명하고 서로 어떤 관계성을 갖는지 설명해주세요.
A3. 리플로우는 처음 노드의 위치, 배치, 크기를 계산하는 레이아웃 작업 이후 요소의 크기가 변하여 다시 계산하는 작업을 의미합니다. 리페인트는 이렇게 요소들의 크기가 변하여 리플로우가 발생한 레이아웃을 다시 화면에 그리거나 요소의 시각적 스타일이 변경되어 화면에 다시 그리는 작업을 의미합니다.

리플로우가 발생하면 리페인트는 반드시 발생하지만 리플로우가 발생하지 않고도 리페인트는 발생할 수 있습니다.

### Q4. TTI와 FCP에 대해 설명하세요.
A4. TTI는 Time to Interactive의 줄임말로 웹 페이지가 완전히 로드되고 사용자가 상호작용을 할 수 있는 시점을 의미합니다.
즉, DNS 조회부터 시작해 페이지의 주요 리소스가 로드되고 메인 쓰레드가 유휴 상태가 되어 사용자 입력에 50ms 이내로 응답할 수 있는 순간까지의 시간을 의미합니다.
FCP는 First Contentful Paint의 줄임말로 브라우저가 처음으로 사용자에게 유의미한 콘텐츠인 텍스트, 이미지, 캔버스를 렌더링하는 순간을 의미합니다. 페이지가 완전히 로드되기 전이라도 화면에 일부 콘텐츠가 나타나면 FCP가 발생합니다.

### Q5. TCP 핸드셰이크는 어떻게 더 안전한 네트워크 연결이 될 수 있게 하나요?
A5. TCP 3방향 핸드셰이크를 통해 데이터 전송 전 클라이언트와 서버 간 연결을 설정하여 안전한 상태인지를 확인합니다.
먼저 클라이언트가 서버에게 연결을 시작하고 싶다는 신호인 SYN 패킷을 보내면 서버는 클라이언트에게 요청을 받았고 연결을 시작하겠다는 응답인 SYN-ACK 패킷을 보냅니다. 클라이언트가 이를 확인하면 데이터 전송을 시작한다는 ACK 패킷을 보내게 되고 이 과정이 완료되면 TCP 연결이 완료되며 클라이언트와 서버가 데이터를 주고 받을 준비가 된 상태라는 것을 알 수 있습니다.
